# Phase 9 research — operational records and durable effects

Researched 2026-09-21. Scope OPS-01..08, CC-05 and operational POL-01. Confidence high on existing code boundaries; new document rendering and file recovery still require executable proof. This is planning evidence, not implementation acceptance.

## Recommended architecture

Keep the current modular .NET application and SQL Server database. Add an Operations application/infrastructure boundary, separate API endpoint modules and business pages under the existing Next.js shell. Reuse identity snapshots, transactional command receipts, opaque ETags, current relationship checks, audit and the persistent job/provider machinery. No document database or second policy graph is needed.

Introduce an OperationalSubject registry with exactly one typed FK to Agency, client relationship, Quote, Policy or ServicingDraft. Use a CHECK for exactly one FK, filtered unique indexes for each typed parent and NO ACTION deletes. Registry registration occurs under the real parent's authorized transaction; it is not permission. A central OperationalScope resolver follows current parent ownership on every list/read/write/download/retry, before command replay. Child records store SubjectId; incident records additionally require an owned PolicyId and exact selected historical source. This realizes the intended WorkRecord supertype without retrofitting or rewriting every existing entity, AuditEvent or OutboxWork. Do not accept cached AgencyId on the registry as authorization. Client-wide lists union only currently accessible relationships; a note for one relationship never becomes global client data.

Expose typed parent entry points and owned IDs in responses; generic subject resolution accepts only closed kinds and actual existing IDs. Add composite constraints where a child carries both subject and parent/version IDs. Reject foreign parent combinations in SQL as well as services. Register retained parents lazily/idempotently or by missing-only backfill; never replace retained keys or JSON.

## Data contracts

| Aggregate | Mutable head | Immutable records and constraints |
|---|---|---|
| Task | title, priority, due date, state, eligible user/team assignment, current ETag | TaskEvent(sequence), checklist definition snapshot and changes, TaskComment, TaskSourceEvent; unique(ruleVersionId, sourceKind, sourceId, eventKey); mandatory reason for complete/reopen; no blind task CRUD affecting referral decisions |
| Note | no editable head needed | scoped internal Note(author/time/body), optional explicit revisions only if source requires; bounded plain text, no inherited public audience |
| File | finalization/screening state | FileObject(storage kind/key, hash, length, detected media, sanitized display filename); generated immutable identity, unique operation key; ready bytes cannot be overwritten |
| Document | subject/type and version pointer | DocumentVersion(fileId, exact source IDs/hash, templateVersionId/hash, rendererVersion, sequence); ready-only preview/download; withdrawal event does not delete historical bytes |
| Thread/message | thread subject/audience, editable message draft and ETag | immutable queued MessageVersion and recipient/attachment-version snapshots, MessageDelivery and attempts; no mixed internal/agency audience |
| Incident | draft/current revision/state/ETag | IncidentRevision, historical occurrence resolution, selected source hash, immutable handoff, append-only ClaimsSummary(provider operation/event identity); no local settlement mutations |
| MID | projection of pending/accepted/rejected submission | owned PolicyMidIntent → MidSubmission + exact items/action/effective date + attempts/response; unique intent association; no CC submissions |

Use existing SettingVersion for published workflow and adapter scenario snapshots, and existing TemplateVersion for document definitions. Phase11 owns administration. Versioned seed definitions must validate their closed schema; an unavailable published rule/template is a visible readiness issue, never an invented default after issue.

Bulk task mutations accept at most100 distinct task IDs and ETags, one explicit action and reason/assignment/due payload. Lock in stable order, authorize all rows and eligible assignees, validate checklist/type completion policy, then write every event and receipt in one transaction. Any conflict rolls all back. Keep selection/input in UI on error. Task auto-creation consumes durable source records/events, not browser reads or transient polling timestamps. Distinguish source resolution from human completion.

## Files and actual PDF generation

Existing AgencyEvidenceFile, QuoteEvidenceFile and ServicingEvidenceFile store byte[] Content in SQL. Preserve these bytes and legacy ownership. A FileObject can reference exactly one existing evidence source through typed nullable FKs, or a newly created local volume object; CHECK and unique indexes prevent ambiguous storage. Downloads of bridged evidence still require the original parent scope and screening eligibility. Do not bulk migrate/delete existing evidence during this phase.

New files use an IOperationalFileStore abstraction and a persistent configured directory outside app/static roots. Stream bounded bytes (accepted API default20MiB; lower per-kind limits allowed), hash while writing an app-generated temporary object, validate a closed PDF/PNG/JPEG allowlist and content signatures, then commit pending metadata plus finalization work. Finalization atomically moves within the same volume, checks hash/length and marks ready only after verification. Recovery handles crash before SQL commit, before rename, after rename and before ready. Orphan cleanup operates only on expired unreferenced temporary objects under a verified root; it cannot delete ready/issued/referenced content. Paths, keys and exception details never enter public responses. Reject traversal, symlinks/reparse escapes, false extensions, unsupported/oversize files and changed bytes. Demo signature screening must be explicitly labelled; do not claim antivirus scanning. Microsoft recommends dedicated storage, server-controlled filenames and server-side limits/type validation: [ASP.NET Core uploads](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0).

Select PDFsharp-MigraDoc Core6.2.4 behind IPolicyDocumentRenderer, pinned centrally with lockfiles. Its official package and source declare MIT licensing: [NuGet](https://www.nuget.org/packages/PDFsharp-MigraDoc/6.2.4), [license](https://github.com/empira/PDFsharp/blob/master/LICENSE). Use declarative, closed template JSON and typed source projections; never execute arbitrary HTML/Razor/scripts from templates. Tables should repeat headings and paginate; cap row/content lengths and render overflow fixtures. [MigraDoc tables](https://docs.pdfsharp.net/MigraDoc/DOM/Contents/Tables.html).

Bundle unmodified IBM Plex Sans regular/bold TTF assets from a pinned official release, include OFL license and source/hash manifest, and register a custom resolver once at process startup. Cover every style/error/bullet font explicitly; no reliance on installed Windows fonts. PDFsharp6.2 Core requires explicit font resolution in portable use: [font resolver](https://docs.pdfsharp.net/PDFsharp/Topics/Fonts/Font-Resolving.html). IBM distributes Plex under OFL: [official font source](https://github.com/IBM/plex). Verify exact TTF assets at implementation; browser WOFF2 files are not interchangeable.

Persist original generated bytes, metadata and SHA256. Retry returns the existing generated version; it must not render fresh timestamps into replacement bytes. A deliberate regeneration creates a separate version and provenance. Render source/template hashes from the stored request and immutable source, verify commercial projection against exact retained version, and derive pre-Phase8-envelope CC projections without rewriting old requests. Existing template seed includes a pending-generation sentence: do not mutate old template content; explicitly render that legacy text as provenance rather than current document state, and publish a new truthful template version for future requests. No PDF/UA or legal certificate conformance claim from library availability alone.

## Message and integration execution

API command families should extend existing operationIds from scripts/openapi-operations.mjs rather than silently rename contracts: task list/detail/create/update/bulk/comment/transition, subject notes, file upload/status/download, document list/version/preview/generation, thread/message drafts/send, pack send/resend, incident draft/detail/history/handoff/contact, MID list/detail/retry. Document a bounded request/response schema, authority, ETag resource, idempotency and safe failure for each in OPERATIONS-CONTRACTS.md; generate TS/OpenAPI using existing generators. No raw storage locators, credentials, provider secrets or arbitrary JSON writes.

Sending snapshots current recipient identity/address and exact ready attachment versions after subject/audience authorization. Drafts can change; queued envelopes cannot. Recheck current sender capability, recipient relationship and audience both before provider execution and before applying outcomes. A revoked/stale operation is recorded as blocked/superseded; it cannot leak through retry. Read scope is separate from capability to send. Cross-subject attachments require an explicit authorized relationship intersection; default reject if not the same operational subject.

Reuse OutboxWork, AdapterAttempt, DemoProviderOperation, SqlJobLeases and the established QuoteDeliveryWorker/ServicingDeliveryWorker split between provider execution and application. Pin exact operation key, scenario version and request hash. Timeout-after-success recovers persisted provider result, without a second provider effect. Apply only under a live owned lease and compare exact identities/hash/result; changed duplicate responses are quarantined. Terminal exceptions generate one task per source failure event. Same-operation retry must preserve immutable message/version selection; explicit resend creates a new delivery operation for explicitly selected unchanged document versions. Provider receipt delivery state and file-generation state remain independently visible.

CancellationNoticeWorker currently records a deterministic receipt but does not render or attach a document. Additive enrichment must preserve those historical receipts, distinguish legacy delivery evidence and associate new actual files/messages without silently resending historical notices. Certificate withdrawal and policy task closure wait until the pinned effectiveAt; only eligible policy-servicing tasks close, never unrelated claims/compliance tasks. Withdrawal changes current availability, not historical bytes. Test future cancellation before/at/after boundary and retries after restart.

## Historical incident precision

Store occurredOn, optional approximateLocalTime, timeZone Europe/London and precision, plus knowledge cutoff fixed at handoff. Do not assign midnight as asserted occurrence. Resolve the set of source-version applicability intervals intersecting the declared local date/time window, clipped by cancellation/expiry and known-at rules. Approximate time remains approximate; do not imply minute precision unless user explicitly records it as exact. Daylight-saving gaps/overlaps require valid offset/disambiguation when an exact instant is requested.

If one materially applicable cover version covers the entire claimed interval, retain the interval and its sole source. If several versions apply or only part of the interval is covered, return candidates with safe dates/labels and require explicit occurrence clarification/selection with a reason; do not confirm coverage merely from a candidate selection. Represent unresolved cover separately from factual draft capture. Extend the existing CommercialIncidentPayload boundary to consume validated occurrence resolution without pretending a representative lookup instant is an observed time. Motor/CC contracts reject incompatible fields; CC location/cover/EL occupation must belong to selected retained cover. Handoff pins the resolution and revision permanently. A later correction is a new revision and explicit new operation after definitive rejection, not changed same-key replay.
