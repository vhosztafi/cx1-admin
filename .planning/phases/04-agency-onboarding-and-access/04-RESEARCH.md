# Agency onboarding and access research

Researched2026-09-14 against repository/source and primary technical documentation. Recommendation: extend the existing modular .NET/SQL architecture; no new identity library, document database or external message provider is needed for this phase.

## Existing implementation and gaps

Agency currently contains Reference/LegalName/State only. PartyDemoSeed creates Brightside and Kingsway as drafts while existing servicing relationships remain available internally. StaffUser has no AgencyId yet; ActorContext and SqlTicketStore deliberately deny external roles. ProductVersion rows are draft configurations, so agency eligibility cannot silently imply published rating readiness. Phase3 filters relationships/clients/contact/support/match data in SQL; retain those boundaries when adding trusted broker identities.

OpenAPI already defines draft/product/evidence/check/activation/abandon/suspend/reactivate/invitation/terms/state-request operations. It lacks source-faithful territory/correspondence/referral/volume modes, full compliance evidence kinds, staged invitation versus delivery state, safe preview routes, agency user mutation/permission requests, actual activity, delivery result reads and a usable notification/check contract. Existing agency-option-mapping.json covers only seven option families. Plan04-01 must expand strict mappings/examples/tests before enabling runtime routes. Preserve existing operation identifiers already referenced by control mappings; never derive runtime completeness from operation count.

The source stages user invitations before activation, requires a broker administrator, states14-day expiry and shows separate countersigning. Source format checks and dropdown selection are visual mock behavior, not proof of verification. Store actual evidence/check provenance and enforce activation in the API. The current source account balances, policies and follow-on tasks are not Phase4 financial implementations.

## Data and transaction design

| Record | Proposed responsibility and invariants |
|---|---|
| Agency / AgencyOnboarding | Existing Agency identity plus OnboardingStep, normalized search/read metadata, current draft revision; unique1:1 typed Details JSON. Optional bounded fields until activation; no optimistic UI-only save. Rowversion on aggregate. |
| AgencyEvidence / AgencyEvidenceFile / AgencyCheckAttempt | Agency-scoped immutable supplied evidence/file bytes/hash and bounded provider/manual attestation; kind/status, relevant-input fingerprint, check-rule version, verified/expiry timestamps. Never reuse evidence from another agency or from stale inputs. Files max10MiB and explicit MIME/extension validation; safe download, no public URL. |
| AgencyProductDraft / AgencyTermsVersion / AgencyProduct | Mutable draft selection and complete published effective-dated snapshot. Integer commission/fee-share bps0..10000; nonnegative exact money. Agency parent lock prevents overlapping versions; agency/version and product-per-version unique. Future scheduled versions resolve by effective time; old terms are immutable. |
| AgencyStateRequest / AgencyTermsRequest | Immutable proposed state/complete terms snapshot and base-agency version, requester/reason; decision status/actor/date. No self-approval; approved and apply are one transaction. Pending proposal does not alter access. Rejection retains proposal and reason. |
| StaffUser / Role / UserRole / Invitation | Nullable AgencyId FK distinguishes internal identity; explicit agency role scope, exactly one agency role and no mixed sets. Invitation rows bind user/agency, token hash, issue/expiry/revoke/accept and delivery ID. Draft staging has no issued token. Resend creates a new token/version and revokes the prior token. |
| AgencyPermissionRequest / AgencyPermissionGrant | Allowlisted agency capability, scope, reason, proposer/decision actor and expiry/revocation. No arbitrary capability names or internal roles. Effective grants resolved on every authorized request. |
| AgencyActivity / AgencyFollowUp | Append-only safe event IDs/actor/time and approved summaries; separate agency-owned scheduled follow-up records, not fake WorkRecord IDs. |
| AgencyNotification / provider receipt | Durable operation identity, audience, protected payload reference, state/attempts and sanitized result. Extend existing OutboxWork/JobAttempt/leases; unique provider operation receipt survives retry/restart. Invitation acceptance remains independent. |

Lock order must be explicit across all services: Agency first, then ordered user IDs, then invitations/proposals/terms as appropriate. Revisit existing client-link/matching lock order before acquiring Agency locks there; don't introduce agency->client versus client->agency deadlocks. A dedicated agency read lock or predicate check cannot replace a coordinated write fence. Tests must race suspension/activation/terms/user edits and intake links. Audit/outbox/receipt and business changes share SqlCommandBoundary's transaction. Authentication/one-time acceptance should use a dedicated transaction, not a response receipt containing credentials.

## Technical sources and resulting choices

- EF optimistic concurrency includes the tracked token in UPDATE/DELETE predicates; SQL Server rowversion is appropriate for aggregate stale-write detection. Keep ETags and domain conflicts separate. [EF Core concurrency](https://learn.microsoft.com/en-us/ef/core/saving/concurrency).
- Multiple SaveChanges calls can participate in one transaction; EF savepoints do not replace the caller's atomic unit, and MARS affects savepoint behavior. Reuse the established boundary and test failure after intermediate saves. [EF Core transactions](https://learn.microsoft.com/en-us/ef/core/saving/transactions).
- Serializable range locking can protect absent/overlapping effective intervals. Our design chooses a stable agency parent lock plus unique constraints and overlap validation for predictable contention. This is an architectural inference, not a claim that rowversion alone prevents interval phantoms. [SQL Server isolation](https://learn.microsoft.com/en-ie/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver16).
- Cookie identity must be revalidated when backend access changes. Extend the current SQL ticket retrieval path to reject inactive agencies/users and rebuild current roles/scope, retaining API401/403 behavior. [ASP.NET Core cookie authentication](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/cookie?view=aspnetcore-10.0).
- Data Protection supports expiring payloads; use purpose-separated protection for local invitation delivery material, with database hash/revocation/one-time consumption providing the lifecycle authority. Encryption alone does not implement revocation. [Limited-lifetime payloads](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/consumer-apis/limited-lifetime-payloads?view=aspnetcore-10.0).
