# Phase 4 data and API decisions

This is the implementation contract supplement for04-01, not an implemented schema. Refine the generated OpenAPI/data dictionary from these decisions before migrations. The existing API prefix is /api/v1; paths below omit it.

## Aggregate and identity

Agency retains its existing ID/reference/legal name/state and adds OnboardingStep1..6, normalized name, RegulatoryReference?, RelationshipManagerId?, and optional projected contacts/address/payment fields. AgencyOnboarding has AgencyId unique/FK, SchemaVersion and strict Details JSON max64KiB. Draft products have own IDs, AgencyId/ProductVersionId unique, integer commission bps and business effective date. Projected fields and Details update together. Missing draft data is omitted; empty text is normalized to omission, explicit invalid null/unknown keys are rejected. Never replace populated legacy details during repeat seed.

04-02 implementation refinement: AgencyOnboarding uses the shared StoredRecord surrogate UUID primary key and a unique AgencyId foreign key. Only legal/normalized name, regulatory reference, relationship manager and current stage are duplicated as relational search/concurrency projections. Contacts, structured addresses, commercial declarations and settlement values remain in the bounded typed JSON; the directory reads the main contact from the current page’s agency-owned JSON. This avoids two authorities for fields that are not searched. Create and save both accept `{details,onboardingStep,products?}` and commit them atomically. Mutation receipts contain only ID and original ETag, followed by a fresh authorized read. Until their owning plans run, user/action counts are omitted and distribution/rating flags remain false without inventing a distribution setting version.

Add StaffUser.AgencyId nullable, FK Agency no cascade. Internal users require AgencyId null and only internal Role.Scope; agency users require one AgencyId and exactly one agency role. Keep normalized email globally unique; changing email or agency association is not a side effect of resending an invitation. Agency user edit supports display name and permitted broker role, never internal authority or agency reassignment. Existing internal user administration remains Phase11. SQL triggers validate UserRole insertion/update/deletion and user agency change; service transactions must support initial user+role creation without leaving a committed mixed/roleless active identity.

04-05 lifecycle refinement: user create responses bind the parent agency ETag; edit/deactivate/reactivate bind the user ETag, and invitation resend/revoke bind the invitation ETag. User edits change display name and one allowed broker role only. Role changes rotate the security stamp and revoke sessions. Agency locking serializes last-active-admin demotion/deactivation checks. Deactivation retains credentials/history while revoking every staged/pending invitation and existing session. Reactivation requires a draft or active agency: a previously credentialed user can become active only in an active agency; an unaccepted user becomes invited with a new staged invitation (draft) or fresh issued invitation (active). No prior invitation or session is revived. A revoked staged user can be deactivated and then restored through this lifecycle without reusing the globally unique email in a second identity. Broker authorization remains closed until04-07; these service commands currently require internal agency administration.

04-05 public user API refinement: preserve `inviteAgencyUser` at POST `/agencies/{agencyId}/invitations`. Its existing service receipt namespace `/api/v1/agencies/{agencyId}/users` remains stable to preserve already committed internal/demo command keys; no second public creation alias is added. The response contains `{id: userId, invitationId}` and the parent agency ETag, with Location pointing to the user read. User edit/state responses contain only `{id}` and user ETag. Invitation resend/revoke responses contain `{id: resultInvitationId, userId}` and invitation ETag; resend is202, revoke200. Scoped user/invitation list and detail reads expose only safe identity/lifecycle fields and row ETags. Lists are bounded with scope/route-bound cursors; invitation history can filter by userId. Storage suspended users project as inactive. Pending invitations past their real expiry project as expired without mutating terminal history. Until04-07, every internal user/invitation route requires current internal agency-admin/system-admin authority. Existing acceptance and Development demo reveal remain separate secret-handling endpoints.

Permissions: agency-read internal agency-admin/system-admin/underwriter/senior-underwriter; agency administration, users and proposals internal agency-admin/system-admin. Approval uses the same authorized role set with ActorId != RequestedBy enforced in service and SQL. Seed a second agency-admin reviewer with an independent account. Broker roles have no internal capabilities; broker-admin can manage own permitted users and request own allowlisted permission. User acceptance activates a credential; it does not change agency state. External route guards require trusted active agency+user on every request.

## State and approval model

Persist AgencyStateRequest with AgencyId, RequestedState(active/suspended), RequestKind(activation/suspension/reactivation), BaseVersion(binary8), ProposedInputFingerprint, RequestedBy, RequestReason, State(pending/applied/rejected/stale), DecisionBy?, DecisionReason?, DecidedAt?. Immutable proposal fields; terminal decision append-only or guarded one-time. Unique live request per agency/kind. No separate approved-but-unapplied window: approving applies under the same transaction, otherwise rollback.

POST /agencies/{id}/activate creates a pending activation proposal (202, ID-only). The existing operation identity is retained but its documented behavior becomes request-countersign; UI uses Request activation at confirmation. POST /suspend and /reactivate similarly request approval. GET /agency-state-requests/{id} shows the bound proposal. POST /agency-state-requests/{id}/decision (approve/reject/reason, If-Match request) is the only application path. Agency version/fingerprint must still equal base, and actor must differ. Rejection does not alter agency. Draft abandon is direct admin action with reason/agency ETag; it retains identity/history and revokes staged/pending invites. No active/suspended abandonment.

All agency mutations acquire Agency UPDLOCK first; then users ordered by ID, then invitation/proposal/terms/evidence as required. Activation checks/evidence writes/staging/terms changes advance agency RowVersion, even under repeated clock timestamps. Recheck current prerequisites inside the lock. Adapt Phase3 CreateRelationship and MatchService link/separate to acquire the relevant agency before client/intake locks; all paths must use one order, including replay prerequisites. Do not add the inverse lock order in only one branch. Tests explicitly race suspension against linking and accepting invitations. Internal contact servicing may continue for retained historical relationships; external writes remain denied by inactive agency.

Proposal creation holds the agency lock but does not change its business RowVersion; BaseVersion captures the current domain ETag and the proposal has its own ETag. This avoids making a proposal stale merely by creating it. A new proposal may atomically mark an existing pending proposal stale only when its base no longer matches the current agency; otherwise reject duplicate live proposals. Applying or rejecting uses the proposal token; applying also requires the unchanged agency base. The same rule covers commercial requests.

## Evidence and checklist

AgencyEvidence holds AgencyId, Kind(fca/toba/pi/financial/sanctions/ownership/dpa/client-money), State, InputFingerprint, RuleVersionId, FileId?, AttestedBy?, RecordedAt, VerifiedAt?, ExpiresOn?, bounded result code/notes. AgencyEvidenceFile owns AgencyId and immutable bytes(max10MiB), hash, safe filename, content type, size, screening state. Composite file/agency FK prohibits cross-agency association. Check attempts append to evidence with provider scenario/rule and sanitized result. No caller-controlled verified actor/time. New evidence supersedes earlier evidence by latest valid kind+fingerprint, without overwriting past attempts.

Separate draft declaration from verified status: a valid FCA reference and arrangesGeneralInsurance dropdown do not satisfy verification. Checklist compares current relevant fingerprint/rule, verified result and expiry. Require typed identity/address/main+compliance contacts; principal for representatives and reject introducer-only arranging; at least one currently effective distribution-eligible product with complete terms; signed current TOBA with attestation/file/date; sufficient unexpired PI evidence; clear financial/sanctions/ownership results; signed DPA; client-money proof when CASS5 applies; viable staged or active broker-admin. Demo thresholds/rule versions are labelled fictional and configurable, not legal certification. Failed/unavailable checks do not become verified through a form edit.

Routes: POST /agencies/{id}/evidence-files binary/multipart plus metadata, GET /agencies/{id}/evidence-files/{fileId}/content attachment download, GET/POST /evidence for provenance/attestation, POST /checks for persisted deterministic attempt, POST /validate returns structured checklist with paths/stage codes and current agency ETag. Mutations require CSRF/key/ETag. File content is not echoed in a replay receipt; API limits bodies before buffering. Download reauthorizes ownership, uses nosniff and attachment disposition; no inline HTML/SVG or filesystem path.

## Terms and product eligibility

AgencyTermsVersion stores immutable complete commercial/settlement/account snapshot, AgencyId/version unique, EffectiveFrom business date, ApprovedRequestId and CreatedBy/time. AgencyProduct rows belong to a terms version, unique version/product; grant references exact ProductVersionId and bps. Initial activation must have at least one eligible product effective on activation date. Phase2 draft definitions get an explicitly labelled distribution-eligibility SettingVersion; they remain non-rateable and not published for underwriting. Later capture/issue additionally checks real product readiness.

For an active agency, POST /terms-requests contains complete future commercial/product snapshot, effectiveFrom, reason and base agency ETag. Proposal decision appends only: new EffectiveFrom must be no earlier than today and strictly later than the latest scheduled version; reject same-date/overlapping/out-of-order schedule. Derive each version's effective end from the next version's start rather than rewriting immutable prior terms. Select current with max EffectiveFrom<=business date. No backdated agreed-term rewrites in MVP. Rejected proposals preserve history. Disabling a product is exclusion from the next full version, not deletion of its previous grant.

Money uses canonical two-decimal nonnegative string input and decimal(19,2); percentages use integer bps0..10000. Flat-rate basis requires flat bps, per-product uses each selected row. Fee split, volume mode/value and minimum override mode/value remain distinct typed answers. No source option is converted into a fake numeric zero to imply approval. Products grant distribution access only; no underwriting authority.

## Invitations and notification security

Draft staged user may have Invitation state=staged without TokenHash/IssuedAt/ExpiresAt/SendJobId. Activation issue assigns fresh32-byte token hash, real-time14-day expiry and protected payload; active direct invites issue immediately. Acceptance state(pending/accepted/expired/revoked) and notification state are independent. Resend creates a fresh issued invitation and revokes previous pending token in one transaction. Unique active issued invitation/user; race acceptance/resend/revoke under agency->user->invitation locks. Require active agency at acceptance; invited user becomes active only after password hashing/credential creation and token consumption commit. Successful acceptance cannot be replayed to reset credentials. Use generic bounded invalid-link response for unknown/used/revoked/expired tokens.

Tokens/passwords never enter ordinary command outcomes, audit JSON, URLs sent to server, logs, screenshots or unprotected job payload. Protect delivery envelope with purpose-separated Data Protection and persistent keys; provider receives decoded content only in worker memory. DB stores token hash and encrypted envelope. Development-only POST /invitations/{id}/demo-link requires current internal agency-user-admin, CSRF and inspection audit; no Idempotency receipt and no cache, never included in list data. Local UI puts token in URL fragment, removes it with replaceState and submits token/password in POST /auth/invitations/accept with antiforgery and bounded rate limit. No automatic sign-in or privilege grant beyond the invitation's saved role.

Notification service uses kind=agency-notification, unique operation ID and provider receipt; retries preserve original message identity. Worker checks current invitation validity before simulated delivery and marks stale queued work superseded; a completed old delivery does not restore token validity. Delivery result reads contain only safe state/attempt code/time. Activation notices and invitation emails explicitly say demo-delivered; no real email. Follow-ups for PI expiry and quarter review persist in AgencyFollowUp with unique source-purpose/date, not generic task IDs until Phase9.

## Read APIs and future owners

Add /agency-relationship-managers and /agency-product-catalog for stable selectable IDs; paged /agencies supports q/state/relationshipManagerId. Detail contains actual agency data, checklist and explicit unavailable sections. /activity and /notifications use scoped safe projections. Agency permission requests/grants have a bounded allowlist (initially bordereau-download), agency scope and approval/revocation provenance. No arbitrary internal permission string may be stored as a grant.

Internal /agencies/{id}/sharing and authenticated broker /agency-context/* use the same safe projection service; the former audits selected agency and the latter derives agency only from stored identity. Cover client identity, own relationship contacts, granted safe instructions and effective capability/product summaries. Counts/cursors exclude hidden records. Policies/quotes/tasks/statements remain unavailable until Phases5/6/9/10; APIs do not fabricate balance0 or foreign policy IDs. Actual statement/export, policy navigation and future grant enforcement stay in ACCEPTANCE-BACKLOG.


### Implemented administrator readiness (04-05)

Readiness derives the administrator prerequisite under the existing agency transaction. The user must belong to this agency and hold the agency-scoped broker-admin role. For draft/active agencies, an active user with a nonempty local password hash qualifies. An invited user qualifies with an owned staged invitation for a draft agency, or an owned pending invitation whose issue time has arrived and expiry is strictly in the future for an active agency. Revoked, expired, not-yet-issued and inactive identities do not qualify. Other agencies and internal administrators never satisfy this prerequisite. This does not grant broker login, distribution access or agency activation; the remaining prerequisites and owning phases still apply.


### Complete terms validation (04-06)

AgencyTermsRules.ValidateProposal validates a complete agreed-terms request independently of a partial onboarding draft. It preserves exact canonical money strings and explicit zero values, requires mode-dependent values, binds the outer effective date to commercialTerms.effectiveFrom, rejects unknown/duplicate/null fields, and normalizes product order. Proposed schedules must begin no earlier than the business date and strictly after the latest scheduled version. Product rows cannot backdate their enclosing version; at least one product begins on that version's effective date so a new full snapshot cannot start with an unintended distribution gap. Later selected product start dates remain allowed.

SnapshotJson excludes the separately retained request reason; its SHA-256 fingerprint covers normalized commercial/settlement/account values, effective date and ordered products. This is a content binding, not an authorization or evidence fingerprint. The proposal service must additionally bind the agency base ETag, requester, evidence/rule/eligibility versions and immutable reason. It must revalidate current eligibility and scheduling under the agency lock when applying a decision. Initial activation extracts a complete snapshot from the saved draft separately; ValidateProposal must not silently overwrite the draft's initial effective-date declarations.


### State proposal persistence (04-06)

AgencyStateRequest is now mapped with an agency base binary(8), content/evidence fingerprint, requested kind/state, immutable requester/reason and a separate rowversion for decisions. A filtered unique index permits one pending request per agency/kind. Rejected/applied decisions require another current internal administrator, a nonblank reason and UTC decision time at or after creation. Automatic stale closure has no human DecisionBy, but requires a reason/time. SQL prevents direct terminal insertion, proposal-content edits (including case-only edits), reopening terminal decisions and deleting history. Proposal storage does not itself alter agency state or publish terms: the forthcoming service must apply those effects atomically with the terminal decision.

The EF migration uses Infrastructure as both project and startup project because it owns the Design package and design-time factory. Build the solution with --no-restore, then use dotnet ef migrations add ... --project backend/src/BackOffice.Infrastructure --startup-project backend/src/BackOffice.Infrastructure --no-build. Creating a proposal leaves the agency domain rowversion unchanged; its own rowversion changes on decision.

### Terms and product persistence (04-06)

AgencyTermsRequest stores the complete ProposedSnapshot and ProposedInputFingerprint (lowercase SHA-256 text64), with independent current internal administration and immutable proposal/terminal decision guards. One pending request per agency is allowed. Version1 uses ApprovedStateRequestId and later versions use ApprovedTermsRequestId; each has a composite request/agency FK and a unique approval reference. This replaces a polymorphic approval ID with enforceable relational provenance. The public approved request identity can be projected from the populated FK.

AgencyTermsVersion retains its full canonical snapshot and strictly appends sequential version numbers and later effective dates. SQL checks applied approval provenance, creator/reviewer equality and later-version snapshot equality. AgencyProduct has AgencyTermsVersionId, exact ProductVersionId, EffectiveFrom and integer commission bps. AgencyId is derived through its immutable parent instead of duplicated. A publication trigger creates the complete 1..3 product set in the same statement; FK/rate/date/unique constraints roll back the parent and all grants on invalid input. Grants reject changes/deletion and must equal the parent snapshot, including creator/time. The additive product migration backfills prior snapshots. Services must insert only the terms parent, acquire the agency lock first, and commit decision plus business effects in one transaction. Eligibility and full business validation remain service responsibilities, not assertions made by storage-only fixtures.

### Current distribution rule and reviewer (04-06)

AgencyDistributionService resolves the highest version effective at the supplied instant in scope agency-distribution. The strict demo rule contains kind=agency-distribution and up to three unique exact productVersionIds; an empty list explicitly withdraws all grants. Missing or malformed current configuration is unavailable and never falls back to older authority. Readiness requires every selected product to be explicitly eligible, one effective today, no repeated product family, an active provider and valid product dates at now (or the selected future start at London midnight). The catalogue reports current distribution eligibility separately from ratingReady=false. These checks are eligibility, not agency approval or underwriting publication.

Repeatable seed adds the rule only when the scope has no versions and adds agency-reviewer@cover.example only when that normalized identity is absent. The reviewer is a second internal agency-admin with the supplied initial demo password; reinitialization never changes existing credentials or roles. Seven fictional accounts now exist. Approval proposal fingerprints must bind the resolved distribution RuleVersionId as well as current evidence and input, and decisions must re-evaluate it within their transaction.

Approval-service integration must retain locks on the current configuration range and product/provider prerequisites until commit (or an equivalent serialized writer protocol). Advisory readiness/catalogue reads alone do not authorize an activation; a newly inserted rule or provider change must not slip between final validation and commit.

### Initial snapshot extraction (04-06)

AgencyTermsRules.ExtractInitial accepts the saved draft and its stored product rows, validates the draft, then extracts only complete commercial/settlement/account/product terms. The initial commercial date may be historical but cannot be after the assessment business date. It is retained exactly, not silently shifted to activation day. Existing product/version consistency applies: no grant precedes the terms date and at least one starts on that date; mismatches require an explicit draft correction. The same complete value/conditional/money/fingerprint logic serves initial and later terms, while later proposals still reject backdating. Draft readiness now includes an initial-terms item so such storage-incompatible dates or incomplete conditional values cannot appear ready. Approval services must call extraction again inside the final transaction; this helper does not approve or publish.

### Terms command service (04-06)

AgencyTermsService separates subsequent agreed-terms commands from the still unfinished state/activation workflow. Propose accepts only active/suspended agencies with an existing initial version, preserves the agency base ETag, and records its own request ETag. A live request conflicts unless its agency base is stale; a replacement closes the old request as stale in the same transaction. Structural canonicalization runs before replay, while date/latest-version rules run after receipt resolution so a committed request remains replayable after its effective date.

The proposal fingerprint binds canonical terms, the current distribution SettingVersion ID, selected product/provider identities and held catalogue rowversions in a deterministic SHA-256 input. Decisions require another current internal administrator, current request ETag and pending state. Approval also rechecks agency base, latest schedule, complete values and product eligibility. Agency-first locking is followed by held identity/role locks, a held distribution-scope range (including new/future versions), and held product/provider rows. Decision, immutable terms/product publication, agency ETag advancement, activity, audit and receipt commit together. Rejection retains history without changing the agency ETag. Services insert only the terms parent; SQL owns product projection.

Public endpoint/DI/UI wiring remains pending. These service tests establish subsequent terms behavior from an explicit initial storage fixture; they do not claim agency activation works. Final acceptance must also exercise configuration/role writer races and public API/browser recovery with the finished workflow.

### Validated activation proposals (04-06)

AgencyActivationService.Propose now captures a pending activation only after current complete readiness passes inside the agency transaction. Shared AgencyApprovalLocks supplies the same held current-authority, distribution-range and product/provider checks used by subsequent terms. Activation additionally retains compliance settings, broker user/role and relationship-manager prerequisites. Its fingerprint binds the agency base, canonical initial terms/distribution version, compliance rule, evidence IDs, broker identity states/security stamps/roles and staged invitation identities. Volatile assessment time is excluded so an unchanged ready draft has stable content; expiry/current-rule validity must be rechecked when applying.

Creation returns the request ID and request ETag without changing the agency ETag/state, issuing tokens, publishing terms or queueing delivery. A duplicate current-base request conflicts; a replacement may close a stale-base request atomically. Authorization precedes replay; a committed receipt remains available after subsequent rule changes. Public registration/endpoints and the independent application command remain pending. AgencyFollowUp is still a planned schema record and must be implemented before activation can claim all required follow-up effects.

### Durable follow-up obligations (04-06)

AgencyFollowUp is now an immutable record with AgencyId, Purpose and DueOn, plus either EvidenceId for pi-expiry or ActivationRequestId for quarter-review. Separate composite source/agency FKs replace an unenforceable polymorphic SourceId. PI due date must equal verified professional-indemnity evidence expiry; quarter review requires the applied activation and its reviewer as creator. Both require current internal administration and source timestamps no later than creation. Filtered unique source/purpose/date indexes prevent duplicate obligations; SQL rejects update/delete and wrong source kinds/ownership. Current storage records an obligation only: omit speculative State/TaskId columns until Phase9 introduces the real task association and materialization lifecycle. The owning activation transaction will compute its London business quarter-review date; no task or notification is created by inserting this record alone.

### Independent activation application (04-06)

AgencyActivationDecisions applies or rejects activation requests under the agency lock with a current independent administrator and request ETag. Approve rechecks the unchanged agency base and current assessment fingerprint/readiness and rejects pre-existing initial terms. Its single command transaction records the decision, activates the agency, captures complete initial terms/product grants, issues all staged invitations, queues protected notices for the agency and each distinct capacity provider, records PI-expiry and three-calendar-month review obligations, appends activity/audit and stores the original receipt. Any failure rolls the entire transaction back, including generated invitation tokens and queued notices. Rejection retains the draft and creates no activation effects.

Activation notices use their own additive agency-activation-delivery SettingVersion (default fictional pass), while invitation delivery retains its existing scope. Both enqueue and worker verify the appropriate scope. Provider notices route to the explicit fictional capacity-demo@cover.example alias and bind the provider name in protected content; operation IDs derive deterministically from activation request/provider IDs. No real messaging or ledger creation occurs. Follow-ups retain real source IDs without task IDs. Public API/DI/UI wiring and suspension/reactivation remain pending.

Approval review hardening: the shared eligibility fingerprint now includes the selected ProductVersion rowversion/product/provider IDs and both Product and CapacityProvider rowversions, alongside canonical terms and distribution rule ID. Current eligibility alone was insufficient when a mutable draft definition changed but remained eligible. Such catalogue changes now invalidate pending terms and activation proposals; held row locks still prevent changes after final validation. The SQL activation test explicitly changes the catalogue while eligibility remains true and requires a fresh proposal.

## Agency association lock ordering

Phase3 relationship creation now locks Agency before ClientAccount. Match decisions lock Agency -> MatchSubmission -> MatchReview -> ClientAccount -> ClientAgencyRelationship. The initial submission agency projection is lock planning only and is revalidated under the child locks. Link/separate checks the locked agency for suspended/abandoned state before any client creation. Historical query/reopen/decline remains available to authorized staff. This serializes association writes with the agency lock used by lifecycle decisions; a waiting command observes committed suspension and fails without effects. Three real-SQL races cover link, separate and the public relationship API, including a child-lock availability probe. This is the prerequisite fence, not a claim that suspension approval or external effective access is implemented.

## Independent suspension transaction

AgencySuspensionService creates a pending suspension proposal for an active agency, retaining its agency base and a deterministic state/base fingerprint; creation leaves agency, users, invitations and sessions unchanged. A different current internal administrator may reject or apply using the request ETag. Applying requires the unchanged active agency base, uses the existing agency-first lock, rotates every scoped user's security stamp, revokes all unrevoked sessions and staged/pending invitations, and commits decision/state/activity/audit/receipt atomically. Duplicate live proposals conflict; a stale-base proposal can be replaced and is closed as stale in that transaction. Current actor authority is checked before receipt replay and held through application.

Individual user status and credentials are deliberately preserved: agency suspension is a separate access condition, and future reactivation must not silently reactivate individually disabled users. Old invitation/token/session history remains revoked rather than deleted. The service touches neither another agency's users nor Phase3 association history or published terms. Reactivation must recheck current prerequisites and arrange fresh invitations when required, without reopening previous invitations. Broker login remains closed until04-07; no public suspension endpoint or effective external scope is claimed by this internal service.

## Reactivation and current approved prerequisites

AgencyReactivationAssessment is a caller-transaction participant that locks the suspended agency and selects its latest approved terms effective on the explicit Europe/London business date. ReadPublished validates the complete immutable snapshot without treating its historical date as a new proposal. Future versions do not replace current commercial inputs until their effective date. Current approved commercial/settlement values replace stale onboarding commercial inputs for assessment; identity/compliance declarations and evidence remain current onboarding facts. Eligibility holds distribution/catalogue rows, evidence holds the compliance rule, and user/role/credential and manager locks remain held through commit. The fingerprint binds agency base, current terms identity, eligibility, evidence IDs, and user/role/credential rowversions. It contains no credential content.

A viable broker administrator must be individually active with a local credential or individually invited with a permitted role and valid email. Invited users are explicitly selected for fresh invitations on approval; individually suspended users remain suspended. Reactivation itself requires a different current internal administrator, unchanged agency/request versions and the current fingerprint. Approval atomically restores agency active state, rotates stamps and revokes any remaining sessions or live invitations, creates fresh invitation identities/tokens for the assessed invited users, and records activity/audit/receipt. Old revoked invitation/session records are never reopened. Rejection and proposal creation have no access or delivery effects. No new terms, activation obligations or duplicate activation notices are created. Public API/DI/UI and external effective authorization remain unfinished.

## Public commercial terms and effective product reads

AgencyTermsEndpoints now registers terms proposals (202 ID-only), scoped request list/detail, independent decisions (200 ID-only), and immutable version history. Proposal/request/decision access requires current internal agency-admin/system-admin; published versions use existing internal agency-read, consistent with existing commercial data visibility. Commands retain strict bounded JSON, CSRF, parent/request ETags, stored scope resolution and original replay. Request reads include exact complete financial/product values, actual actor labels and own ETag; no caller-selected approver or agency scope is accepted.

Version history is paginated at the cursor's explicit asOf time. Its Europe/London date selects current/scheduled/historical status, including the exclusive next-version effectiveTo. Approval IDs identify activation versus subsequent terms provenance. Parent locking keeps published rows and agency ETag coherent while reading. Active/suspended /products now returns only currently effective grants from the current approved version, with termsVersionId and exclusive effectiveTo; future selections remain visible in full version snapshots. Draft and abandoned records retain their draft selection/history behavior. This grants no rating/underwriting authority. Terms activity summaries describe publication/rejection accurately.

## Trusted scope resolution foundation (04-07)

AgencyAccessRules permits only an exclusive recognized agency role on an active agency and active stored user. Broker-admin has the dedicated context/sharing read and own-user/permission-request capabilities; broker-user/readonly have only context/sharing reads. No internal capability or bordereau download is inferred. Future persisted grants will be resolved separately rather than encoded as role claims.

AgencyScope.Resolve is a caller-transaction participant, not an endpoint. It requires the caller's trusted agency claim to equal both the requested agency and current persisted StaffUser.AgencyId; current role rows must exactly match the principal. It holds agency, user, membership and role rows through the protected operation, using agency update locks for mutation capabilities and shared hold locks for reads. AsNoTracking prevents a caller's tracked stale entity from overriding current database facts. The order remains agency then user then roles; future authentication must coordinate credential/session locks with that order. No supplied agency parameter can broaden scope. Scope changes/role loss produce403 before downstream queries or receipts.

This foundation deliberately does not enable broker login or change existing internal PartyScope. Wire safe projections and identity/session rebuilding before enabling external accounts. SQL coverage proves authorization holds block a concurrent suspension until transaction end, subsequent suspended/disabled/changed-role requests deny, and the existing active-user role SQL invariant remains enforced.
