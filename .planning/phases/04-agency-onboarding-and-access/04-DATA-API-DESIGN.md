# Phase 4 data and API decisions

This is the implementation contract supplement for04-01, not an implemented schema. Refine the generated OpenAPI/data dictionary from these decisions before migrations. The existing API prefix is /api/v1; paths below omit it.

## Aggregate and identity

Agency retains its existing ID/reference/legal name/state and adds OnboardingStep1..6, normalized name, RegulatoryReference?, RelationshipManagerId?, and optional projected contacts/address/payment fields. AgencyOnboarding has AgencyId unique/FK, SchemaVersion and strict Details JSON max64KiB. Draft products have own IDs, AgencyId/ProductVersionId unique, integer commission bps and business effective date. Projected fields and Details update together. Missing draft data is omitted; empty text is normalized to omission, explicit invalid null/unknown keys are rejected. Never replace populated legacy details during repeat seed.

04-02 implementation refinement: AgencyOnboarding uses the shared StoredRecord surrogate UUID primary key and a unique AgencyId foreign key. Only legal/normalized name, regulatory reference, relationship manager and current stage are duplicated as relational search/concurrency projections. Contacts, structured addresses, commercial declarations and settlement values remain in the bounded typed JSON; the directory reads the main contact from the current page’s agency-owned JSON. This avoids two authorities for fields that are not searched. Create and save both accept `{details,onboardingStep,products?}` and commit them atomically. Mutation receipts contain only ID and original ETag, followed by a fresh authorized read. Until their owning plans run, user/action counts are omitted and distribution/rating flags remain false without inventing a distribution setting version.

Add StaffUser.AgencyId nullable, FK Agency no cascade. Internal users require AgencyId null and only internal Role.Scope; agency users require one AgencyId and exactly one agency role. Keep normalized email globally unique; changing email or agency association is not a side effect of resending an invitation. Agency user edit supports display name and permitted broker role, never internal authority or agency reassignment. Existing internal user administration remains Phase11. SQL triggers validate UserRole insertion/update/deletion and user agency change; service transactions must support initial user+role creation without leaving a committed mixed/roleless active identity.

04-05 lifecycle refinement: user create responses bind the parent agency ETag; edit/deactivate/reactivate bind the user ETag, and invitation resend/revoke bind the invitation ETag. User edits change display name and one allowed broker role only. Role changes rotate the security stamp and revoke sessions. Agency locking serializes last-active-admin demotion/deactivation checks. Deactivation retains credentials/history while revoking every staged/pending invitation and existing session. Reactivation requires a draft or active agency: a previously credentialed user can become active only in an active agency; an unaccepted user becomes invited with a new staged invitation (draft) or fresh issued invitation (active). No prior invitation or session is revived. A revoked staged user can be deactivated and then restored through this lifecycle without reusing the globally unique email in a second identity. Broker authorization remains closed until04-07; these service commands currently require internal agency administration.

04-05 public user API refinement: preserve `inviteAgencyUser` at POST `/agencies/{agencyId}/invitations`. Its existing service receipt namespace `/api/v1/agencies/{agencyId}/users` remains stable to preserve already committed internal/demo command keys; no second public creation alias is added. The response contains `{id: userId, invitationId}` and the parent agency ETag, with Location pointing to the user read. User edit/state responses contain only `{id}` and user ETag. Invitation resend/revoke responses contain `{id: resultInvitationId, userId}` and invitation ETag; resend is202, revoke200. Scoped user/invitation list and detail reads expose only safe identity/lifecycle fields and row ETags. Lists are bounded with scope/route-bound cursors; invitation history can filter by userId. Storage suspended users project as inactive. Pending invitations past their real expiry project as expired without mutating terminal history. Until04-07, every internal user/invitation route requires current internal agency-admin/system-admin authority. Existing acceptance and Development demo reveal remain separate secret-handling endpoints.

Permissions: agency-read internal agency-admin/system-admin/underwriter/senior-underwriter; agency administration, users and proposals internal agency-admin/system-admin. Approval uses the same authorized role set with ActorId != RequestedBy enforced in service and SQL. Seed a second agency-admin reviewer with an independent account. Broker roles have no internal capabilities; broker-admin can manage own permitted users and request own allowlisted permission. User acceptance activates a credential; it does not change agency state. External route guards require trusted active agency+user on every request.

## State and approval model

Persist AgencyStateRequest with AgencyId, RequestedState(active/suspended), RequestKind(activation/suspension/reactivation), BaseVersion(binary8), ProposedInputFingerprint, RequestedBy, RequestReason, State(pending/applied/rejected/stale), DecisionBy?, DecisionReason?, DecidedAt?. Immutable proposal fields; terminal decision append-only or guarded one-time. Unique live request per agency/kind. No separate approved-but-unapplied window: approving applies under the same transaction, otherwise rollback.

POST /agencies/{id}/activate creates a pending activation proposal (202, ID-only). The existing operation identity is retained but its documented behavior becomes request-countersign; UI uses Request activation at confirmation. POST /suspend and /reactivate similarly request approval. GET /agency-state-requests/{id} shows the bound proposal. POST /agency-state-requests/{id}/decision (approve/reject/reason, If-Match request) is the only application path. Agency version/fingerprint must still equal base, and actor must differ. Rejection does not alter agency. Draft abandon is direct admin action with reason/agency ETag; it retains identity/history and revokes staged/pending invites. No active/suspended abandonment.

All agency mutations acquire Agency UPDLOCK first; then users ordered by ID, then invitation/proposal/terms/evidence as required. Activation checks/evidence writes/staging/terms changes advance agency RowVersion, even under repeated clock timestamps. Recheck current prerequisites inside the lock. Adapt Phase3 CreateRelationship and MatchService link/separate to acquire the relevant agency before client/intake locks; all paths must use one order, including replay prerequisites. Do not add the inverse lock order in only one branch. Tests explicitly race suspension against linking and accepting invitations. Internal contact servicing may continue for retained historical relationships; external writes remain denied by inactive agency.

Proposal creation holds the agency lock but does not change its business RowVersion; BaseVersion captures the current domain ETag and the proposal has its own ETag. This avoids making a proposal stale merely by creating it. A new proposal may atomically mark an existing pending proposal stale only when its base no longer matches the current agency; otherwise reject duplicate live proposals. Applying or rejecting uses the proposal token; applying also requires the unchanged agency base. The same rule covers commercial requests.

## Evidence and checklist

AgencyEvidence holds AgencyId, Kind(fca/toba/pi/financial/sanctions/ownership/dpa/client-money), State, InputFingerprint, RuleVersionId, FileId?, AttestedBy?, RecordedAt, VerifiedAt?, ExpiresOn?, bounded result code/notes. AgencyEvidenceFile owns AgencyId and immutable bytes(max10MiB), hash, safe filename, content type, size, screening state. Composite file/agency FK prohibits cross-agency association. Check attempts append to evidence with provider scenario/rule and sanitized result. No caller-controlled verified actor/time. New evidence supersedes earlier evidence by latest valid kind+fingerprint, without overwriting past attempts.

Separate draft declaration from verified status: a valid FCA reference and arrangesGeneralInsurance dropdown do not satisfy verification. Checklist compares current relevant fingerprint/rule, verified result and expiry. Require typed identity/address/main+compliance contacts; principal for representatives and reject introducer-only arranging; at least one currently effective distribution-eligible product with complete terms; signed current TOBA with attestation/file/date; sufficient unexpired PI evidence; clear financial/sanctions/ownership results; signed DPA; client-money proof when CASS5 applies; viable staged or active broker-admin. Demo thresholds/rule versions are labelled fictional and configurable, not legal certification. Failed/unavailable checks do not become verified through a form edit.

Routes: POST /agencies/{id}/evidence-files binary/multipart plus metadata, GET /agencies/{id}/evidence-files/{fileId}/content attachment download, GET/POST /evidence for provenance/attestation, POST /checks for persisted deterministic attempt, POST /validate returns structured checklist with paths/stage codes and current agency ETag. Mutations require CSRF/key/ETag. File content is not echoed in a replay receipt; API limits bodies before buffering. Download reauthorizes ownership, uses nosniff and attachment disposition; no inline HTML/SVG or filesystem path.

## Terms and product eligibility

AgencyTermsVersion stores immutable complete commercial/settlement/account snapshot, AgencyId/version unique, EffectiveFrom business date, ApprovedRequestId and CreatedBy/time. AgencyProduct rows belong to a terms version, unique version/product; grant references exact ProductVersionId and bps. Initial activation must have at least one eligible product effective on activation date. Phase2 draft definitions get an explicitly labelled distribution-eligibility SettingVersion; they remain non-rateable and not published for underwriting. Later capture/issue additionally checks real product readiness.

For an active agency, POST /terms-requests contains complete future commercial/product snapshot, effectiveFrom, reason and base agency ETag. Proposal decision appends only: new EffectiveFrom must be no earlier than today and strictly later than the latest scheduled version; reject same-date/overlapping/out-of-order schedule. Derive each version's effective end from the next version's start rather than rewriting immutable prior terms. Select current with max EffectiveFrom<=business date. No backdated agreed-term rewrites in MVP. Rejected proposals preserve history. Disabling a product is exclusion from the next full version, not deletion of its previous grant.

Money uses canonical two-decimal nonnegative string input and decimal(19,2); percentages use integer bps0..10000. Flat-rate basis requires flat bps, per-product uses each selected row. Fee split, volume mode/value and minimum override mode/value remain distinct typed answers. No source option is converted into a fake numeric zero to imply approval. Products grant distribution access only; no underwriting authority.

## Invitations and notification security

Draft staged user may have Invitation state=staged without TokenHash/IssuedAt/ExpiresAt/SendJobId. Activation issue assigns fresh32-byte token hash, real-time14-day expiry and protected payload; active direct invites issue immediately. Acceptance state(pending/accepted/expired/revoked) and notification state are independent. Resend creates a fresh issued invitation and revokes previous pending token in one transaction. Unique active issued invitation/user; race acceptance/resend/revoke under agency->user->invitation locks. Require active agency at acceptance; invited user becomes active only after password hashing/credential creation and token consumption commit. Successful acceptance cannot be replayed to reset credentials. Use generic bounded invalid-link response for unknown/used/revoked/expired tokens.

Tokens/passwords never enter ordinary command outcomes, audit JSON, URLs sent to server, logs, screenshots or unprotected job payload. Protect delivery envelope with purpose-separated Data Protection and persistent keys; provider receives decoded content only in worker memory. DB stores token hash and encrypted envelope. Development-only POST /invitations/{id}/demo-link requires current internal agency-user-admin, CSRF and inspection audit; no Idempotency receipt and no cache, never included in list data. Local UI puts token in URL fragment, removes it with replaceState and submits token/password in POST /auth/invitations/accept with antiforgery and bounded rate limit. No automatic sign-in or privilege grant beyond the invitation's saved role.

Notification service uses kind=agency-notification, unique operation ID and provider receipt; retries preserve original message identity. Worker checks current invitation validity before simulated delivery and marks stale queued work superseded; a completed old delivery does not restore token validity. Delivery result reads contain only safe state/attempt code/time. Activation notices and invitation emails explicitly say demo-delivered; no real email. Follow-ups for PI expiry and quarter review persist in AgencyFollowUp with unique source-purpose/date, not generic task IDs until Phase9.

## Read APIs and future owners

Add /agency-relationship-managers and /agency-product-catalog for stable selectable IDs; paged /agencies supports q/state/relationshipManagerId. Detail contains actual agency data, checklist and explicit unavailable sections. /activity and /notifications use scoped safe projections. Agency permission requests/grants have a bounded allowlist (initially bordereau-download), agency scope and approval/revocation provenance. No arbitrary internal permission string may be stored as a grant.

Internal /agencies/{id}/sharing and authenticated broker /agency-context/* use the same safe projection service; the former audits selected agency and the latter derives agency only from stored identity. Cover client identity, own relationship contacts, granted safe instructions and effective capability/product summaries. Counts/cursors exclude hidden records. Policies/quotes/tasks/statements remain unavailable until Phases5/6/9/10; APIs do not fabricate balance0 or foreign policy IDs. Actual statement/export, policy navigation and future grant enforcement stay in ACCEPTANCE-BACKLOG.


### Implemented administrator readiness (04-05)

Readiness derives the administrator prerequisite under the existing agency transaction. The user must belong to this agency and hold the agency-scoped broker-admin role. For draft/active agencies, an active user with a nonempty local password hash qualifies. An invited user qualifies with an owned staged invitation for a draft agency, or an owned pending invitation whose issue time has arrived and expiry is strictly in the future for an active agency. Revoked, expired, not-yet-issued and inactive identities do not qualify. Other agencies and internal administrators never satisfy this prerequisite. This does not grant broker login, distribution access or agency activation; the remaining prerequisites and owning phases still apply.
