# Phase 10 finance contract

Status: implementation contract, 2026-09-24. All states below are planned until their owning Phase 10 summary and `10-VERIFICATION.md` provide native SQL and saved browser evidence. The decoded original is `docs/design/source/prototype-template.txt:2824`; `docs/design/finance-source-ledger.json` preserves direct control and display source identities. The Phase 9 handoff is `.planning/phases/09-tasks-documents-communication-and-incidents/09-PHASE10-HANDOFF.md`.

The finance ledger stores both the current decoded source-file SHA-256 and the prior inventory's source hash separately. They differ; exact current line text and all 24 raw direct control IDs are checked against the current files, so no hash equality is inferred across the two source representations.

## Identity, money and posting

The existing `IssueFinancialObligation`, component and `JournalLine` are authoritative insurance movements. Their exact policy/term/transaction/agency/relationship/provider/terms-version and decimal values are never recalculated from current rates. The insurance journal requires a source component and closed account-code set, so receipt, bank match, refund payment and manual correction use separate additive cash/adjustment records. A unified ledger projection has one `(sourceKind,sourceId,lineId)` identity per movement. A `receipt` posting records cash once into suspense; a later `receipt-application` or `receipt-application-reversal` has `CashDelta=0` and changes the debtor and suspense balances once. Allocation never duplicates receipt cash. Every debit/credit pair balances in GBP. Policy effective date and London posting date are separate fields. API money is a canonical signed or nonnegative decimal string with two digits after the point, within the existing decimal(15,2) individual storage range (13 integer digits); parse exactly, reject exponent/comma/NaN and overflow. Checked aggregate sums may exceed the per-row range and must produce an explicit out-of-range error, never truncation or JavaScript floating-point rounding. Client-side arithmetic uses integer pence within the safe integer bound.

New first-issue posting calls `AccountingPeriods.HoldAsync` inside its issuing transaction and saves `AccountingPeriodId`/`PostingDate` before sealing. Existing sealed first issues without those fields remain in period read models using original `PostedAt` converted to Europe/London date. Do not backfill sealed rows. Servicing/cancellation retain their held posting date. Period filter is from-inclusive/to-exclusive on posting date, even for a backdated effective movement. Annual seeded accounting periods are retained; user statement windows can be monthly, fortnightly or custom. A closed period blocks new postings. A later correction posts to a held open period, with original source ID, reason and separate signed movement, never an update to old history.

## Debtor, invoice, cash and statement

`Settlement='net-remittance'` yields an agency receivable for saved `InvoiceDue=NetDue`; `separate-payment` yields the saved gross relationship receivable and a separate broker payable. Never infer debtor from whichever agency owns the policy today. Invoice due date uses the saved agency terms version and explicit statement/processing basis; a terms change does not move historical due dates. Agency balance is signed sum of its posted receivable movements and cash applications. Invoice paid/outstanding/credited/write-off status is derived only from saved allocation, credit and adjustment evidence, never from journal posting alone.

For agency A and window `[from,to)`, `opening = sum(signed movements before from)`, `period = sum(signed movements from through before to)`, `closing = opening + period`. Debit is positive and credit negative in running balance. The same cutoff and source set govern overview, list and statement. An empty window can have a nonzero opening. Negative closing displays as credit balance. Statement generation pins agency/terms identity, requested window, source cutoff/IDs/hash, ordered rows, exact file bytes/hash and creator/time; any later change yields a distinct version. List/detail/download always recheck current finance or explicitly granted agency scope, including before receipt replay and before count/pagination. Historical file permission is not grandfathered.

A receipt is an immutable positive GBP cash fact with operation/import identity, received date, bank reference and explicit payer kind (unidentified/agency/relationship). Payer assignment is audited; unidentified receipts cannot allocate. An `Allocation` links receipt and invoice/credit application, amount, actor/time and operation; reversal appends `ReversalOfId`/reason. The receipt source posts `CashDelta=+amount` and `InternalDelta=-amount`; an application posts `DebtorDelta=-amount`, `InternalDelta=+amount`, `CashDelta=0`, and its linked reversal posts the opposite noncash deltas. The total active allocations cannot exceed either receipt residual or invoice eligible amount. A unique reversal identity prevents double reversal. All mutations lock the current scope first, then receipt and sorted invoice/credit IDs, then the eligible posting period, using one consistent order; reread and validate all residuals under locks. ETags help stale input but are not the sum invariant. Wrong currency, cross-debtor/agency assignment and negative/zero/overflow amount reject atomically. Same command key and same normalized intent replays the original result after current authorization; changed intent conflicts. Persist unique business operation identities beyond command-receipt cache expiry.

## Bank reconciliation

`BankLine.ImportKey` is a unique original import identity. Reimport of that exact key reuses the original line; equal date/reference/amount with a different key is a distinct imported record and only a duplicate candidate. The Phase 10-06 match source is a posted receipt cash movement with a durable Receipt row; paid refund, insurer settlement and fee drawing sources join only when their durable rows and SQL source-binding guards are added together with a native SQL test in their owning plans. Signed amount/currency must agree; partial and split matches are permitted up to each residual. Reversal is append-only, reasoned and unique per original match. Duplicate exclusion retains both imported records, evidence of comparison, actor/reason/time and cannot target an already matched line. Bank line and posted receipt residuals are both visible for the reconciliation window (bank value date and cash posting date respectively); a later bank value date may match an earlier posted receipt. Each nonzero residual requires a current reasoned explanation before completion; explanation remains a displayed audit exception and never creates a synthetic balancing journal. A later match invalidates a prior explanation in an open period when its saved residual no longer equals the current residual. Completed target residuals are displayed as of their completion cutoff, so a later cross-period bank match does not rewrite the closed period's exception. The close consumer must preserve these visible exceptions rather than clear a banner by subtracting an invented number.

## Refund authority and demo payment

Posted credit first offsets eligible unpaid debt. Cash entitlement is the lesser of remaining applicable credit and collected cash traceable to the same debtor/payee, minus prior paid/reserved refunds. Thus unpaid invoice 100/credit 100 permits cash 0; paid 100/credit 30 permits at most 30; paid 10/credit 100 permits at most 10 after the remaining credit offsets debt. Account net balance alone does not prove payee or collected provenance. A refund request pins original transaction/credit, payee relationship, source receipt(s), amount and reservation; competing requests serialize under the same residual locks. Rejection records reason and releases reservation audibly. Approval follows a versioned demo rule with limit and required distinct actors; the prototype £250 second-approval example is an illustrative seed, not a regulatory assertion. Requester cannot approve own request. Role, current authority, limit and rule version are rechecked before decision and replay.

Queueing an approved refund pins exact payment operation and reserves its amount; it does not mean cash was paid. A persistent deterministic local adapter stores one provider outcome independently from the local paid posting/application. States distinguish requested, pending approval, approved, queued, uncertain, provider acknowledged/application pending, demo paid, definite rejection and failed. Timeout after success, lost response or application crash resumes the same operation. Changed intent under a key conflicts and a second key cannot reserve/pay the same entitlement. No real transfer or external bank instruction occurs.

## Bordereau and period closure

A bordereau batch pins provider, product/schema version, statement window, source membership, exact posted amounts and row snapshots. Draft mapping corrections may change export identifiers (policy/provider product/agency reference) but never contractual premium, tax, fee or commission. Every exclusion has reason/actor/time. A changed draft creates a successor version and invalidates prior validation; only an exact version with zero unresolved row failures is eligible for CSV export and submission. CSV has fixed column order, canonical decimal text, RFC-style quotes for delimiter/quote/newline and an explicit escaped representation for untrusted text beginning with spreadsheet formula characters; numbers retain their genuine sign. Generated bytes/hash are immutable. Submitted versions remain downloadable under current authority; a later correction is a linked successor, not a rewrite. Exact version/hash and stable adapter operation are required for deterministic demo submission; provider outcome and local applied submission status remain separately recoverable. No real insurer transmission occurs.

Close period uses the same `AccountingPeriods.HoldAsync` lock ordering as issue/servicing/cash posting and rechecks blockers while held: pending postings, unexplained reconciliation, acknowledged but unapplied payment and required reporting prerequisites. Save close actor/reason/cutoff/checklist. Existing posted rows, statement/batch bytes and period boundaries remain immutable. Any later correction is an auditable new posting in an eligible open period linked to the original, so historical as-of and current corrected views can both be explained.

## API, role and state rules

Separate read/command endpoints own ledger/accounts/statements, receipts/allocations, bank reconciliation, refunds/payment, bordereaux/submission and periods/corrections. Finance read/command/approval limits are distinct capabilities. Existing system-admin, underwriter or agency roles do not imply finance approval. A broker can download only its own statement or bordereau version when the corresponding current grant permits it; no generic finance ledger. All list counts, detail/downloads and command receipt replay apply current stored actor, agency/relationship/provider scope first. Mutations require CSRF, an idempotency key, strong If-Match where a mutable head exists, exact decimal strings and domain error codes that preserve client input. Successful command receipts contain only safe identifiers/ETags, not bank payload, statement bytes, adapter secrets or unredacted PII. Audit records exact source/actor/reason/old and new state; financial rows are never silently deleted.

UI destinations: `/accounting` overview, transactions, broker accounts, payments, reconciliation, bordereaux, refunds and selected record/version; agency Open in Accounting carries its agency ID; policy Finance uses its own scoped finance read model; Admin Open bordereaux lands on the real batch destination while Phase 11 retains the source control owner. All source displays/KPIs state their posting/received/earning basis, and all actions show the saved result rather than a toast-only claim.

### Endpoint and DTO boundary

These are target API families; individual route registration, operation IDs and generated TypeScript names are finalized with their implementation slices. Finance command bodies never accept actor, role, tenant, computed residual or provider outcome fields. Read DTOs carry exact record/version ID, canonical amount strings, source date and posted date where applicable, state, safe reference and an ETag for mutable heads.

| Family | Read and command intent | Capability and scope | Representative domain errors |
| --- | --- | --- | --- |
| Ledger/account/policy finance | List/detail, period and agency filter, transaction drill-through | `finance-read` internally; policy finance also needs current policy scope | `finance-scope-denied`, `amount-out-of-range`, `period-invalid` |
| Statement | Generate/list/detail/download exact version | `finance-read` + `statement-generate`; external download only current own agency grant | `statement-window-invalid`, `statement-source-changed`, `statement-unavailable` |
| Receipt/allocation | Record/assign/list/detail, allocate, reverse with reason | `finance-cash-write` plus current debtor/payer scope | `payer-unidentified`, `debtor-mismatch`, `allocation-exceeds-residual`, `allocation-already-reversed` |
| Bank reconciliation | Import/list/detail, match, reverse, exclude, explain | `finance-reconcile` on current period and source | `bank-import-conflict`, `match-exceeds-residual`, `matched-line-cannot-exclude`, `variance-unexplained` |
| Refund/payment | Request/detail/decide, queue demo payment, attempts/status | `finance-refund-request`, independent `finance-refund-approve` with versioned amount limit, `finance-payment-execute` | `refund-not-collected`, `refund-already-reserved`, `self-approval`, `approval-limit`, `payment-operation-conflict` |
| Bordereau | Generate/detail/version, correct/exclude/validate/export/submit/history | `finance-bordereau` and provider scope; external download requires current own agency grant | `batch-invalid`, `batch-version-changed`, `batch-already-submitted`, `row-money-immutable` |
| Period/correction | Review/close, reasoned post correction | `finance-period-close` or `finance-correction-post` | `period-closed`, `period-has-blockers`, `correction-unbalanced` |

Transport errors use the existing API convention: 400 malformed body, 401 unauthenticated, 403 role denial, 404 inaccessible object, 409 stale/conflict/domain precondition, 412 wrong strong ETag, and 422 structurally valid but unacceptable finance amount or mapping. The implementation plans must settle exact operation IDs and generated clients without changing these semantic boundaries.

### Versioned demo configuration

Seed `finance-refund-rule-v1` as an immutable demo rule: one independent approver up to and including £250.00, two distinct independent approvers above £250.00; no approver may be the requester and each still needs current amount authority. This illustrates the source threshold only and is not a production compliance limit. Phase 11 may publish a successor; an in-flight request remains pinned to v1 while current authorization is still checked. Seed deterministic adapter scenarios `success`, `reject`, `fail-once` and `timeout-after-success` as immutable setting versions for refund payment and bordereau submission. The selected scenario is pinned when queuing; retrying the same operation never silently switches it. These local outcomes never call a bank or insurer.
