# API conventions v1

Contract-first REST JSON under `/api/v1`. The Next.js application and API share a browser origin through a reverse proxy; the .NET API owns authentication, authorisation and business transactions. UI routes are not API routes. The existing sales funnel remains unchanged; these contracts do not assert compatibility with its current transport.

## Representation and ownership

Use UUID identities, human-readable references for display, UTC ISO-8601 instants with explicit offsets, ISO local dates and decimal strings with exactly two fractional digits for money. Include GBP currency where amounts cross an aggregate boundary. Arrays of risk items use stable UUIDs. An omitted optional property differs from an explicit empty value. Reject unknown write properties; never accept actor, computed premium, authority, status or audit fields through a general entity update.

Draft risk replacement uses the partial policy schema. The service creates an immutable revision, validates answer kinds/reference membership and returns completeness errors separately. Rating/issue enforce full product-specific completeness in addition to structural schema validation. Issued snapshots are read-only. Each operation uses a bounded DTO, with separately allowlisted internal and agency views where needed. Restricted support information never enters proposal, rating or insurer-export DTOs.

Mutable resource responses supply an opaque strong `ETag`. Read responses include links by UUID; storage paths, SQL rowversions, secret hashes and integration credentials are not DTO fields. Collection responses are `{items, nextCursor, totalCount}`; totalCount is computed within the same access scope and may be omitted for costly queries. Page size defaults to 25, maximum 100. Cursors bind filters, ordering and access scope, and expire; invalid cursors return 400. Ordering always has an ID tie-breaker. Server allowlists sort/filter fields; no raw SQL/filter expressions.

## Authentication and request security

Local sessions use an opaque Secure HttpOnly `__Host-cover-session` cookie, Path=/ and SameSite=Lax. HTTP-only local development may use a separately named non-Secure development cookie; never weaken the production cookie. The API establishes an antiforgery cookie/request-token pair; the UI obtains its request token from `/auth/csrf` and sends `X-CSRF-Token` on all state-changing requests, including sign-in/sign-out. Explicitly public authentication endpoints work without a business session; they still require antiforgery and their purpose-bound challenge/token where applicable. Rate-limit anonymous authentication/token endpoints and return non-enumerating responses for reset requests.

Sign-in with required MFA returns a short-lived challenge identity and no authenticated business session. TOTP/recovery verification completes the challenge atomically. Temporary challenges and enrolment secrets are purpose-bound, expiring, never logged and returned only to the entitled client. Login/enrolment/reset responses use `Cache-Control: no-store`. Do not cache personalised API responses in Next.js shared caches. Password/identity/role changes revoke or revalidate sessions as specified in PERMISSIONS.md.

OpenAPI declares cookie authentication and the CSRF header scheme together for mutations. Scheme presence describes transport; .NET must actually validate antiforgery and per-operation permissions. Public auth endpoints explicitly override session security. Object and field scope is checked before returning collections, downloading files or evaluating commands. An inaccessible ID returns 404, authenticated insufficient capability on a visible resource returns 403.

## Writes, concurrency and replay

Use POST for explicit business commands, PUT for a complete mutable DTO replacement and DELETE only for eligible draft items/leases. Issued records are never deleted. Mutations of an existing aggregate require `If-Match`; absence returns 428 and a mismatched current ETag returns 412. The response to 412 gives a conflict code and reload instruction, not another user's hidden changes. Draft editing also requires the active lease token; an ETag does not bypass the lease. Policy issue checks both draft revision and policy aggregate concurrency within one SQL transaction.

Business-effect commands require `Idempotency-Key`, 16–200 printable characters, generated by the caller per intended operation. Scope is authenticated user/agency plus canonical route and target; compute a canonical request hash including body and semantic command headers, excluding the retry's obsolete If-Match. Authenticate, authorise and validate key syntax first. A completed matching request returns its original status/body/resource identities before checking the now-stale ETag; changed request content with the same key returns 409 `idempotency-conflict`. Never replay data after access has been revoked. The ETag returned with replay describes the original response; clients reload before further edits.

Authentication and self-account/security endpoints are excluded from the business replay cache. Never store passwords, MFA seeds, challenge tokens, reset tokens or recovery-code responses in IdempotencyRecord. Single-use challenge/token consumption and security-state transitions provide their own atomic duplicate defence; secret disclosure is one-time and is not replayable. Network uncertainty requires checking current security state or starting a new authorised challenge.

Concurrent same-key commands serialize on the database uniqueness/transaction boundary. The loser reloads the committed result; on timeout return retryable 409 `operation-in-progress` with Retry-After rather than execute twice. Domain writes, audit, outbox jobs and command result commit together. A rollback stores no successful result. Cache retention defaults to seven days, but policy/finance/job operation keys remain uniquely constrained for the life of the business record. Do not use a cache as the sole payment/bind duplicate defence.

202 means durable work has been accepted, not completed. It returns a job ID and Location to the scoped job status endpoint; polling is read-only. Issue can return 201 with the created policy transaction while its documents/emails are pending. Job failure does not reverse an issued contract. The client retains its command key on network timeout and queries/retries that same operation.

## Party command refinements

Client updates and relationship creation require the client ETag. Contact creation requires the relationship ETag; contact update/end/make-primary require the contact ETag while locking the parent relationship. Flag creation requires the origin relationship ETag; flag amend/end require the flag ETag. Match decisions require the review ETag. The operation's x-etag-resource extension names this precondition resource. Creation of a child returns the new child's response ETag, not its parent's token.

SqlCommandBoundary stores an optional original strong response ETag alongside the status/body; older receipts without this metadata replay with no ETag. Handlers save within the open transaction to generate rowversion before returning it. Only a bounded strong opaque ASCII ETag is allowed; weak tags, control characters, embedded quotes and arbitrary response headers are rejected. Failure after a handler flush still rolls back the whole command. A later resource edit does not change the original replay response.

Support-flag mutation responses use PartyMutationReceipt containing only id, with the version in the ETag header. The client separately fetches current details under support read permission. Sensitive flag snapshots/reasons never enter ordinary activity or generic command response storage. Flag detail/history has dedicated capability checks; safe instruction lists count only explicitly granted active records and expose no hidden totals. Declined consent is not an accepted FlagWrite basis and causes validation failure without persistence.

ClientSummary explicitly distinguishes unavailable policy/quote data from an available empty portfolio. /clients/{id}/records must not claim an empty live portfolio when its modules are unavailable. MatchReview uses an immutable MatchSubmission with an optional real quote link, plus pinned rule and typed comparison evidence; embedded IDs must match their top-level identities at runtime. Link associates only the submitting relationship. Query records an information request; it does not imply delivery. Reopen retains all trail entries and cannot undo progressed quote/policy effects. CLI-01 linked business-record acceptance remains pending Phases 5/6.

These are implementation contracts; Phase 3 endpoint behavior remains unverified until its owning plan is executed.

## Errors

Use `application/problem+json` with `type`, `title`, `status`, stable `code`, `traceId`, optional safe `detail` and `errors` entries `{path,code,message}`. Validation paths are JSON Pointers. Do not include stack traces, database names, credentials, raw provider payloads or another agency's identifiers. UI error decisions use code, not translated message text.

| Status | Cases |
|---|---|
| 400 | Malformed JSON, invalid query/cursor, unsupported media input |
| 401 | Missing/expired sign-in; no business-data disclosure |
| 403 | Missing capability, failed CSRF, self-approval, authority outside granted dimensions |
| 404 | Missing or inaccessible object |
| 409 | Invalid lifecycle transition, duplicate key with changed intent, edit lease conflict, closed period, exhausted account residual |
| 412 / 428 | Stale / missing required write precondition |
| 413 / 415 | Upload too large / unsupported file type |
| 422 | Well-formed but incomplete/invalid domain data, unresolved required referral, stale rating/acceptance |
| 429 | Rate limit, with Retry-After |
| 503 | Required service temporarily unavailable; retry only with the same operation identity |

## Files, reports and configuration

Uploads accept bounded multipart file bytes and typed metadata, default maximum 20 MiB configurable by kind. Detect content type, sanitise display filename, reject unsupported content, compute SHA-256 and keep pending content unavailable until storage finalisation succeeds. Download the exact authorised version with Content-Disposition and safe media type; do not provide arbitrary local paths or remote fetch URLs. Export creates a durable job with pinned query/time/actor scope; reauthorise before delivering the generated artifact. Counts and exports share report measure/filter definitions.

Published product/configuration versions are immutable. Edit a draft, validate, approve where required, then publish with non-overlapping effective dates. Commands pin configuration identities in downstream results. Admin cannot submit executable script/templates. Matching, workflow, authority and rating rules use typed versioned rule structures with bounded operators.

## Foundation diagnostic operation

`POST /api/v1/admin/diagnostic-probes` is a Development-only operational endpoint, absent from production routing. It requires a current internal system administrator (`integration-admin`), CSRF and one 16–200 character `Idempotency-Key`. The exact body is `{scenario: "success" | "reject" | "fail-once" | "timeout-after-success"}`. Unknown properties and unsupported scenarios are rejected. It queues a fictional foundation probe, not a business transaction. Initialization supplies four versioned scenarios; the command pins the latest effective version and commits job, audit and replay receipt together. A 202 response contains a Job DTO and a `/api/v1/jobs/{id}` Location. Identical replay returns the original accepted response even when the worker has since advanced; poll Location for current status. Changed input under the same key returns 409. Current authorization is checked before replay.

The foundation implementation of `GET /api/v1/jobs/{id}` exposes diagnostic jobs only, to their creator or an internal integration administrator. Inspection of another creator's job writes a redacted audit event before returning it. Missing/inaccessible/business job IDs return 404 until the owning feature implements subject scope. Responses contain only the documented Job fields and a rowversion ETag: no raw request/result, provider operation key, lease token, exception message or credentials. Unknown internal error codes map to `job-failed`. The successful result resource ID comes from a committed diagnostic receipt. Operational lists, settings editing and manual retry are separate implementations; this endpoint does not implicitly grant them.

## Contract verification

Support flags: internal list/detail/history require support-internal-read; create/update/end require support-write, CSRF, Idempotency-Key and strong If-Match. Creation uses the origin relationship version; later changes use the flag version. The service locks all old/new grant relationships and origin in deterministic order before locking the flag, validates active membership for creation/amendment, and commits flag/grants/full restricted history/fixed activity together. Resolution remains allowed after an origin relationship/contact ends. Unchanged declarations with a new review/reason are recorded as reviewed; other edits are amended. Current capability/object scope precedes replay; new-write review dates are checked using the London business date after replay lookup, so old successful receipts remain replayable after their original review date. Invalid/declined consent is rejected before hashing or persistence. Command bodies contain only {id}, with the original saved ETag; clients fetch details through a currently authorized GET. Raw instructions, category, reason and history never enter the generic receipt.

Support instruction preview requires relationship-read and records an inspection audit containing only the relationship identifier. It returns only explicitly granted, active-person-contact wording as id/personId/instruction/reviewOn, with paging based on that exact safe projection and no totalCount. The normal support-safe-read-explicit-grant route is registered but intentionally denied by the current internal-only identity capability mapping; it does not activate broker authentication. Flag-specific activity is included only for support-internal-read actors, and uses fixed labels without flag IDs or sensitive text. Other readers' activity counts/cursors exclude these events entirely.

Relationship contacts: GET list/detail requires relationship-read; POST create, PUT update, POST make-primary and POST end require contact-write and CSRF. Routes are under /api/v1/relationships/{relationshipId}/contacts. Creation requires the relationship's strong If-Match; individual changes require the contact's strong If-Match. All writes require Idempotency-Key. Current scope and supplied reusable person are checked before cached replay; successful replay returns its original body/status/ETag before mutable version/state checks. Contact updates cannot retarget Person or alter canonical identity. First contact is primary automatically; promoting another contact atomically demotes the prior primary. Demoting/ending a primary while other active contacts remain requires selecting a replacement first (409). End requires reason, preserves history and stores actor/time/reason, while response DTOs omit private ending reason and actor. List defaults to active contacts; includeEnded=true includes history. Activity publishes fixed safe summaries and verifies actual contact/client/relationship scope before exposing links.

Foundation manual recovery: Development-only `POST /api/v1/jobs/{id}/retry` requires internal system-admin integration-retry capability, CSRF, Idempotency-Key, the exact strong rowversion If-Match and a nonblank reason (maximum 1000 characters). Missing version returns 428; stale version returns 412. Replay of an authorized successful command precedes the stored job's current ETag/state checks. Only exhausted diagnostic failures classified provider-unavailable, provider-timeout or attempts-exhausted qualify. Definitive rejection, invalid payload, provider identity conflict, pending/leased/successful work and a fully consumed recovery allowance return 409.

The initial six-attempt limit can be expanded twice, to twelve and eighteen, by distinct audited recovery commands. Attempt numbers, pinned scenario and provider operation identity never reset. Each authorized cycle repeats the bounded retry delay schedule. The SQL constraint bounds the persisted allowance and attempt count. Prior JobException and AdapterAttempt evidence remains; current OutboxWork state identifies ongoing recovery. A reason-bearing authorization audit and safe command audit share the correlation ID. Development-only POST /api/v1/admin/jobs/retry-batch accepts 1–100 distinct job IDs with exact ETags and a shared reason. It uses the same permission and command key requirements, sorts IDs into a stable lock order, and applies every recovery inside one SQL command transaction. Any inaccessible, ineligible or stale item aborts the entire batch. The 200 result contains sorted job IDs. Replay hashes the normalized selection and reason; ETags remain preconditions rather than intent, so reordered selections and old ETags replay a prior success without expanding budgets twice.

Foundation operational lists: `GET /api/v1/admin/jobs` requires integration administration and currently lists diagnostic work only; `GET /api/v1/admin/audit` requires internal system-admin audit access and includes only event types with reviewed fixed summaries. Both record a safe inspection audit before returning data. Audit response projection excludes raw reasons and before/after JSON. New business event types require a reviewed projection before inclusion.

List parameters are strict: unknown/repeated parameters, invalid states, malformed IDs, invalid dates or invalid page sizes return 400. Audit instants require a time-zone offset. Page size is 1–100 (default 25). Opaque Data Protection cursors expire after 15 minutes and bind the authenticated user, endpoint, filters and page size; changing any of these requires restarting pagination. Filters and access restrictions apply before counts and pages. Pages use a fixed creation/event time cutoff, descending time plus ID ordering and an offset. New records after the cutoff do not enter subsequent pages; job state changes remain live, so changing states can move results while browsing. This is a browsing cursor, not a transactional export snapshot.

OpenAPI 3.1.1 is chosen to share JSON Schema 2020-12 policy shapes. Validate the document, local references, unique operation IDs, schemas/examples, security declarations and control-to-operation mappings. Schema checks do not prove authorization, SQL locks or runtime OpenAPI conformance; feature phases require direct API and integration tests.

## Reviewed filter semantics

All/Any is omission, never a literal backend value. Resolve agency, user, provider, product and binder labels to scoped IDs. Filters apply before paging/counts; inaccessible rows are excluded before totals. Status labels map to actual resource enums (Onboarding=draft, Referral required=referred; Renewing means active term with open renewal, not a new persisted policy state). Search status is a resource-specific projection; unsupported kind/status pairs yield no matches, never broaden scope. Inception-from is inclusive Europe/London contractual date; reference search is normalised prefix matching. Due windows exclude completed/cancelled tasks: overdue is before current local midnight, today is that local day, next-seven-days is from local midnight through the next seven calendar days exclusive.

Finance filterStatus projections: outstanding means positive unpaid invoice/refund/payable residual; paid means settled cash obligation; allocated means fully matched receipt/bank line; exception means rejected/failed or unmatched reconciliation item. Unsupported projections on a tab return no rows and are disabled in its UI. The period filters both from (inclusive) and to (exclusive) in the tab's documented posting/received/submission date basis. Statements calculate opening before from, period movements and closing before to; signed balances may be credit. Agency-statement summary listing is finance-restricted. Underwriter report/search filter resolves responsible underwriting user on the source record/version, not report runner. Custom periods require valid from/to and retain the report's effective/processed basis.

Incident occurredOn and optional approximateLocalTime preserve uncertainty. Derive occurredAt only with a verified offset/time; date-only incidents require reviewing every applicable version interval on that date when cover changes within it, and capture never asserts coverage. Unknown third-party involvement remains unknown. Full source incident categories remain distinct. Details include reporting route, reporting person, factual location/item/ownership and indicative positive value. Claimed value is not a reserve, payment or admission. Revalidate exact policy/version ownership and permissible document audience before demo-provider handoff.

List status projections are distinct from persisted state: policy renewing is active with an open renewal; quote quoted is current unexpired terms-ready/accepted, quote expired is expired unbound terms, referral-required is referred with an unresolved decision. When state and status are both supplied they intersect. Task Medium maps to normal; unknown option labels are rejected instead of silently ignored.

Foundation integration settings: GET /api/v1/admin/integrations requires integration-admin and returns the latest effective version per known diagnostic scenario, using protected pagination. GET /api/v1/admin/integrations/{id} reads a specific effective diagnostic version. Generic/unimplemented adapter settings remain hidden. The typed response contains scenario, version, demo mode, initial six-attempt budget and base delays; enabled reflects whether this host runs the Development diagnostic worker. Stored scenario JSON must exactly match its known scope and typed contract; malformed configuration produces a safe 503. Each successful read is audited. Settings editing/publishing belongs to the later configuration phase.
